Pipefy Validator

Ferramenta de QA pra detectar divergências estruturais entre pipes do Pipefy e flows do Activepieces (iPaaS), antes e depois de deploys. Garante que cópias de pipes ficam idênticas e captura drift antes que vire incidente em produção.

Visão geral

O Validator extrai a estrutura completa de um ou mais pipes via GraphQL do Pipefy, compara contra outro pipe (ou contra um baseline JSON salvo) e gera um relatório com todas as divergências em 7 categorias. A interface roda em Docker na porta 8080.

Stack técnica

  • Robot Framework 7+ com RequestsLibrary e JSONLibrary pra extração e comparação
  • Python 3.11 + Flask servindo o dashboard (porta 8080)
  • Docker Compose com volumes pra config/, results/ e snapshots/
  • Pipefy GraphQL API (https://api.pipefy.com/graphql)
  • Activepieces REST API pra módulo iPaaS

Fluxo típico de uso

  1. Você está prestes a fazer um deploy de um pipe entre HMG e PRD.
  2. Antes do deploy: gera um snapshot do pipe HMG (modo Snapshot · Gerar). Salva como baseline.
  3. Faz o deploy manualmente no Pipefy.
  4. Depois do deploy: roda Cross-env HMG vs PRD pra confirmar que tudo bateu.
  5. Se sobrar divergência: abre o relatório no V2, filtra por categoria, copia o que precisa ajustar.
  6. Periodicamente roda Batch em vários pipes do mesmo ambiente pra detectar drift sem deploy.

Single-env

Compara 2 pipes dentro do mesmo ambiente (mesmo token, mesma organização). Caso de uso clássico: você criou uma cópia de um pipe pra testar mudanças e quer garantir que a cópia está idêntica à origem antes de alterar uma das duas.

Em V2, a seleção de pipe origem/destino na UI foi removida porque o backend atual usa sempre os UUIDs hardcoded em config/<preset>.robot. Cada preset (ex: fourd_hmg.robot) define um par fixo de pipes. Pra rodar com pipes diferentes, edite o preset ou crie um novo via modal Gerenciar Ambientes.

Cross-env

Compara entre 2 ambientes diferentes. Cada cross-env é um arquivo config/cross_*.robot que tem 2 conjuntos de credenciais e 2 pares de pipes (origem/destino em organizações distintas).

Padrão de naming:

  • cross_<env>_selfcheck: mesmo ambiente nos dois lados (sanity, deve dar 0 diffs)
  • cross_<src>_x_<dst>: comparação cruzada entre dois ambientes distintos

Crie novas configs cross via modal Gerenciar Ambientes ou direto em config/cross_*.robot.

Snapshot · Gerar

Captura o estado completo de um pipe (estrutura + automações + metadata) em um arquivo JSON em snapshots/. Use antes de qualquer mudança que você queira ter um baseline pra comparar depois.

O dropdown Ambiente · Pipe lista todos os pipes de todos os ambientes configurados. Selecionar uma combinação preenche o nome do arquivo automaticamente (ex: mesa_credito_pf_fourd_hmg_20260428_173856.json). O label pode ser editado manualmente.

Snapshot · Comparar

Lê um snapshot salvo (baseline) e compara contra o estado live de um pipe escolhido. O dropdown Pipe atual lista todos os pipes de todos os ambientes. Quando o nome bate com o do baseline, mostra badge mesmo pipe do baseline; caso contrário, pipe diferente.

ⓘ
Como o backend respeita a seleção O frontend envia pipe_uuid e pipe_repo_id no payload do /api/run. O backend repassa via --variable PIPE_DESTINO_UUID:xxx pro Robot, que sobrescreve o valor hardcoded no active.robot. Mesma mecânica do Snapshot Gerar.

Batch

Validação em massa: roda self-check (origem = destino) em vários pipes em sequência. Cada pipe é comparado contra ele mesmo, garantindo que a estrutura está íntegra (detecta drift causado por edições manuais sem deploy).

A lista vem de config/batch_pipes.json. Cada pipe tem env_id que indica de qual ambiente é. O frontend filtra os pipes pelo ambiente ativo no Single-env, e o backend passa --variable BATCH_ENV:<env_id> pro Robot pra evitar tentar acessar pipe de outra organização (que daria PERMISSION_DENIED).

⚠
Seleção visual no Batch Marcar/desmarcar checkbox na UI é visual. O backend sempre executa todos os pipes do batch_pipes.json filtrados por env. Implementar respeito real à seleção da UI está no roadmap A+.

iPaaS

Validação de flows do Activepieces, plataforma de integração separada do Pipefy. Faz inventário dos flows de um projeto, compara metadados (status, triggers, steps, conditions, conexões) e gera relatório similar ao Pipefy.

Sub-modos:

  • CT-IPAAS-01 Self-Check: extrai flows do mesmo projeto duas vezes e compara (sanity)
  • CT-IPAAS-02 Cross-Env: compara flows entre 2 projetos Activepieces
  • CT-IPAAS-03 Snapshot Gerar: salva baseline JSON
  • CT-IPAAS-04 Snapshot Comparar: confronta live vs baseline

Categorias de divergência

Toda divergência detectada é classificada em 1 das 7 categorias abaixo. Categorias podem ser filtradas na tela de Resultados (sidebar esquerda).

TagNomeO que detecta
SFStart FormCampos do formulário inicial: nome, tipo, obrigatoriedade, opções
FAFases & CamposEstrutura por fase: nomes, ordem, tipos de campo, defaults, help text
LBLabelsEtiquetas (existência, nome, cor)
ASAuto · StatusAutomações ativas/inativas, tipo de ação, evento (card_moved, card_late, etc)
ADAuto · Fase DestinoResolução de fase destino/evento por nome via phase map
AHAuto · HTTPConfiguração de HTTP: URL, método, body, headers
ACAuto · ConditionLógica condicional: operador, valor (ignora IDs numéricos)

Presets e configs

Cada ambiente Pipefy tem um arquivo config/<env_id>.robot com credenciais e pipes hardcoded. Quando você executa uma run, o backend copia esse arquivo pra config/active.robot antes de chamar o Robot Framework. Pra cross-env existe config/active_cross.robot que vem do config/cross_*.robot escolhido.

Pra criar um novo preset: edite via modal Gerenciar Ambientes ou copie um arquivo .robot existente como template e ajuste manualmente.

Snapshots como baseline

Snapshots são arquivos JSON em snapshots/ contendo a estrutura completa de um pipe num momento específico. Convenção de nome: <label>_<YYYYMMDD_HHmmss>.json.

O conteúdo inclui:

  • Metadata (timestamp, label, nome do pipe, versão da ferramenta)
  • Estrutura completa do pipe (fases, campos, start form, labels)
  • Lista de automações com todas as configs (HTTP, conditions, fase destino)

Deploy e rebuild

Mudanças em arquivos volume-mount (config/, results/, snapshots/) refletem instantaneamente sem rebuild.

Mudanças em server.py, web/, resources/ ou tests/ exigem rebuild da imagem: 

cd C:\Users\FourD\Documents\robothz\pipefy
docker-compose down
docker-compose up --build -d
Start-Sleep -Seconds 8
Start-Process "http://localhost:8080"

Troubleshooting

HTTP 401 Unauthorized

Token expirou ou está inválido. Renove via Gerenciar Ambientes ou edite config/environments.json.

PERMISSION_DENIED

Token não tem acesso ao pipe ou organização. Geralmente acontece quando você tenta rodar batch com pipes de organizações diferentes ou quando o usuário do token não foi adicionado ao pipe.

HTTP 409 Conflict no /api/run

Já existe uma run em execução. Aguarde terminar ou reinicie o container pra limpar o estado.

Mock zumbi na tela de Resultados

Run abortou antes de gerar validations.json. O backend agora grava um fallback com status: EXECUTION_FAILED e o frontend mostra empty state explícito com mensagem do erro real (parseado do output.xml) e hint sugerindo correção.

Tela de Configuração não atualiza após editar ambiente

Cache do navegador. Faça Ctrl + F5 pra forçar recarga dos assets.

Roadmap A+

O V2 atual segue a decisão D (MVP Honesto): features cuja UI mentia foram removidas até o backend respeitar de verdade. O A+ é o caminho pra restaurar essas features com integração completa frontend ↔ backend ↔ Robot Framework.

Concluído

  • Snapshot Gerar com pipe alternativo via --variable PIPE_ORIGEM_*
  • Snapshot Comparar com pipe alternativo via --variable PIPE_DESTINO_*
  • Batch filtrado por env via --variable BATCH_ENV
  • Single-env com dropdowns de pipe origem/destino respeitados (resolve UUID via ENVS_DATA e manda no payload)
  • Cross-env com 2 dropdowns dinâmicos baseados nos env_ids do cross selecionado
  • Categorias Pipefy filtráveis via --variable CATEGORIES_FILTER:SF,FA,.... comparator.resource usa keyword Categoria Habilitada pra pular blocos de categorias não selecionadas
  • Categorias iPaaS filtráveis via mesmo CATEGORIES_FILTER aceitando IF (Inventário/Status), IT (Trigger), IS (Steps). ipaas_comparator.resource com keyword Categoria iPaaS Habilitada
  • Cancel real de run: POST /api/run/cancel chama proc.terminate() + kill() de fallback. Backend usa subprocess.Popen em vez de run pra manter referência ao processo
  • run_id sincronizado: frontend substitui o ID gerado client-side pelo real do backend antes de navegar pra Execução
  • Batch respeitando seleção da UI: frontend manda pipes_selected[] com UUIDs, backend filtra via --variable BATCH_SELECTED:uuid1,uuid2 e batch.robot aplica filtro adicional ao BATCH_ENV
  • Health Check mode V2: 6º item na sidebar de modos. Roda tests/healthcheck.robot com 9 verificações (Pipefy API, Automações, Comparação estrutural, Comparação automações, Snapshot ciclo, Relatório JSON, iPaaS API, iPaaS self-check, iPaaS snapshot)
  • Endpoint POST /api/configs: cria config/cross_<id>.robot a partir de 2 envs do environments.json. Modal "Criar nova configuração cross-env" virou form real com 2 dropdowns + input

Pendente

  • Validação E2E manual dos 17 cenários do HANDOFF (acumulou ~15 ondas de mudança)
  • Tokens client-side (cada usuário cola seu próprio Bearer no navegador)
  • Segurança: tokens em secrets manager, auth Flask, rotacionar JWTs, sanitizar f-string injection

Segurança

  • Tokens em plaintext no environments.json → migrar pra secrets manager
  • Endpoints Flask sem auth → adicionar autenticação básica antes de prod
  • _generate_robot() tem f-string injection com token: tratar como sensitive

Suítes de teste

O projeto tem 3 suítes de teste independentes cobrindo backend, frontend e integração HTTP. Total atual: 90 testes em ~8 segundos. As suítes não dependem uma da outra: pytest e vitest rodam offline, smoke precisa do container ativo.

SuíteStackCobreLocal
pytest Python + Flask test client 41 testes: funções puras + endpoints HTTP do server.py tests/python/
vitest Node + jsdom-free 35 testes: funções utilitárias do frontend V2 tests/frontend/
smoke Robot Framework + RequestsLibrary 14 testes: HTTP contra container vivo na porta 8080 tests/smoke_api.robot

pytest · server.py

Testa as funções críticas do backend isoladamente. Usa monkeypatch.chdir + reimport do módulo pra isolar cada teste num filesystem temporário.

O que cobre

  • Funções puras: _load_envs, _save_envs, _generate_robot, _generate_ipaas_robot, _extract_fail_from_output_xml (com detecção de 401/PERMISSION_DENIED/404/timeout)
  • Endpoints HTTP: /api/configs, /api/environments, /api/v2/environments, /api/snapshots, /api/batch, /api/results, /api/run, /api/status
  • Comportamento do /api/run: 409 quando run em curso, geração de fallback EXECUTION_FAILED quando Robot aborta sem produzir validations.json, propagação de --variable PIPE_ORIGEM_* e BATCH_ENV
  • Segurança: garante que /api/v2/environments não vaza token, session_cookie nem csrf_token

Como rodar

pip install -r requirements-dev.txt
python -m pytest tests/python/
ⓘ
Mock do Robot Framework Os testes que envolvem /api/run usam monkeypatch em subprocess.run pra retornar um MagicMock instantâneo. Nenhum test pytest dispara o Robot de verdade nem chama o Pipefy.

vitest · frontend utils

Testes unitários das funções utilitárias puras do V2 frontend. As funções foram extraídas pra web/designs/assets/v2_utils.js (UMD-like: funciona em browser via window.V2Utils e em Node via module.exports).

O que cobre

  • String utils: slugify, escapeHtml, truncMid
  • Cross-env: parseCrossConfigMeta, getCrossTokenStatus
  • Snapshot: computeSuggestedSnapLabel
  • Categorização de divergência: categorize, severityOf (mapeamento das 7 categorias SF/FA/LB/AS/AD/AH/AC)

Como rodar

npm install
npm test

smoke · Robot Framework HTTP

Roda contra o container vivo em http://localhost:8080. Útil pra validar deploys e checar contratos da API após mudanças. Não dispara o Robot de verdade (só lê endpoints idempotentes e faz 1 POST defensivo com payload inválido).

O que cobre

  • Páginas: redirect da raiz, V1 legacy, V2 configuração, V2 docs, V2 help
  • API: 9 endpoints validando shape de resposta + sanitização de tokens
  • Cache: assets V2 servem com header no-store
  • Defensive: POST /api/run com body inválido não retorna 500

Como rodar

docker-compose up -d
python -m robot --outputdir results/smoke -t "HC-*" tests/smoke_api.robot
✓
Bug detectado pelos próprios testes O smoke HC-13 achou que POST /api/run com body "not_a_dict" retornava HTTP 500 (AttributeError: 'str' object has no attribute 'get'). Fix aplicado em server.py: usa request.get_json(silent=True) + valida isinstance(raw, dict).

Glossário

Pipe
Estrutura de processo no Pipefy. Tem fases, campos, automações.
Fase
Etapa dentro de um pipe. Cards transitam entre fases.
Card
Item de trabalho no pipe (uma instância do processo).
Automação
Regra disparada por evento (card_moved, card_late, etc) que executa ação.
Self-check
Comparação de um pipe contra ele mesmo, deve dar 0 divergências por definição. Detecta corrupção de leitura ou drift inesperado.
Drift
Diferença entre o estado esperado (baseline) e o estado atual de um pipe.
Cross-env
Comparação entre 2 ambientes diferentes (ex: HMG vs PRD).
Preset
Arquivo .robot em config/ com credenciais + pipes hardcoded de um ambiente.
iPaaS
Activepieces, plataforma de integração separada do Pipefy.
Decisão D
MVP Honesto: features cuja UI não viajava no payload foram removidas até backend suportar (ver Roadmap A+).
